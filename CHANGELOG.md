# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.RedisTimeSeries` -- a real `Scry.Core.EngineBehaviour` implementation over RedisTimeSeries, via `redix`. Validates the time-series kind against a second real product after `scry_engine_ch`, this time one with no query language at all to translate into, only a fixed numeric-range command shape (`TS.RANGE key from to [FILTER_BY_VALUE min max]`). `scry_time_series`'s own `LAST`-lowering pass rewrites `LAST <duration> OF <field>`/`LAST <from> TO <to> OF <field>` into an ordinary comparison (or two, `AND`-combined) before any engine ever sees it -- the identical "zero new code needed" finding `scry_engine_postgrex`'s own TimescaleDB validation and `scry_engine_ch`'s own landing both already established, so this package needed no time-series-specific code of its own either.
  Every row has exactly two fixed fields, `"timestamp"` (Unix milliseconds) and `"value"` (a double) -- a RedisTimeSeries key holds nothing but an ordered sequence of samples, no broader per-row schema. Both are genuinely, always non-`nil` (a "gap" in a series is an absent sample, never a present row with a `nil` value, confirmed directly) -- `describe_source/2` reports both as `nullable: false` honestly, not as a simplifying assumption.
  `Scry.Engine.RedisTimeSeries.RangeQuery` translates every `WHERE` predicate leaf on `"timestamp"`/`"value"`, combined only via `AND`, into `TS.RANGE`'s own bounds -- exactly wide enough for both `LAST` forms and nothing wider, since `TS.RANGE` has no boolean query language at all (an `OR`/`NOT` node, an `IN` leaf, or any other field name all decline outright, unlike `scry_engine_elasticsearch`'s own real `bool` query support). On `"timestamp"`, `:gt`/`:lt` adjust by one millisecond (`TS.RANGE`'s own bounds are always inclusive, and a timestamp is always a whole millisecond integer, so this is an exact adjustment, not an approximation); on `"value"`, the identical adjustment has no safe equivalent for a real double, so `:gt`/`:lt` decline there instead of risking a silently wrong boundary. Multiple bounds on the same axis narrow to the tightest, confirmed by property test to hold for an arbitrary mix, not just the hand-picked examples the unit tests cover.
  `ORDER BY`/`LIMIT`/`OFFSET` are deliberately never pushed down to `TS.RANGE` at all: it has no server-side sort-direction or offset concept, and pushing down only `COUNT` while leaving direction to be applied afterward would silently return the wrong *set* of rows whenever the requested order is `DESC` (the first `N` in ascending storage order is not the same rows as the first `N` sorted descending) -- reasoned through directly, not discovered as a bug. The full matching range is always fetched and handed to `Scry.Core.QueryOps.run_flat/3` for `ORDER BY`/`LIMIT`/`OFFSET`/projection instead, the same "clear what's already handled, delegate the rest" split `scry_engine_elasticsearch` already established, except here nothing about ordering/pagination was ever pushed down in the first place.
  `GROUP BY`/aggregates/`HAVING`/`DISTINCT` all decline -- `TS.RANGE`'s own native `AGGREGATION` buckets by *time*, not by an arbitrary field the way SQL `GROUP BY` does, and Scry's own language has no time-bucketing construct yet to translate a real `GROUP BY` into that shape even in principle (the identical gap the corrected `scry_engine_timescaledb` entry already found from the SQL side). Key names are validated only as a non-empty string, not against the identifier-safety pattern this family's SQL/HTTP-based siblings use -- `redix` sends each command argument as its own length-prefixed RESP bulk string, never concatenated into a parsable command grammar, so there is no injection surface to guard against here, and a real Redis key name routinely contains characters (`:`, `/`) an identifier pattern would wrongly reject.
